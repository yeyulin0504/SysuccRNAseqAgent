# SYSU RNA-seq Agent 前六项任务汇报整理

## 总体判断

当前项目已经不是一个简单脚本，而是一个 **RNA-seq 流程执行底座**：它能生成 `project.json`，校验本地 FASTQ，上传到服务器，生成并提交远程脚本，轮询状态，下载结果，并可发送通知。后续最合理的方向，不是推倒重写，而是在这个底座上补 **对话能力、报告能力、示例演示**，逐步发展成面向实验室同学的低门槛 agent。

---

## 1. 别人的 agent 一般如何发布

现在主流 agent 很少只靠一种形态发布，通常是多种方式并存：

1. **开源源码仓库**
   - 方便研究、复现、二次开发
   - 适合高校、实验室、开发者群体

2. **Python 包 / CLI**
   - 适合技术用户、本地运行、服务器集成和自动化调用

3. **Web SaaS**
   - 面向普通用户，开箱即用
   - 但依赖云端服务和外部网络

4. **自托管 / 私有化部署**
   - 适合对数据安全、内网部署有要求的单位
   - 在科研、医疗、企业场景更重要

5. **桌面 / 本地客户端**
   - 面向低门槛个人使用场景
   - 特别适合实验室同学在自己的电脑上使用

### 对我们项目的启发

我们这个项目最适合采用分层发布思路：

- **对实验室同学**：优先提供桌面/本地 GUI
- **对老师和维护者**：保留 Python 包 / CLI
- **对后续实验室推广**：预留私有化部署空间

也就是说，不必只选一种，而是做成：

**“桌面入口 + 可审计执行底座 + 后续可扩展部署方式”**

## 2. 别人的 agent 文章一般怎么写，需要哪些元素

agent 文章通常不是在写“一个大模型本身”，而是在写 **一个能完成真实任务的系统**。重点通常不在“模型多强”，而在“这个系统怎样解决问题”。

### 常见论文结构

1. **引言**
   - 问题背景
   - 传统方法的不足
   - 为什么需要 agent 形式

2. **系统设计 / 方法**
   - 整体架构图
   - LLM 负责什么
   - 工具/工作流负责什么
   - 状态与数据如何流转

3. **任务流程**
   - 用户如何提出需求
   - 系统如何追问和补齐信息
   - 如何调用工具
   - 如何得到结果

4. **实验与评测**
   - 成功率
   - 效率
   - 与传统方式对比
   - 用户负担是否下降

5. **案例展示**
   - 展示一个或多个真实使用闭环

6. **局限性与风险**
   - 哪些步骤仍需人工确认
   - 哪些地方不稳定
   - 数据隐私和结果解释边界

### 对我们项目的写法建议

如果以后写文章，建议主线写成：

**“构建一个面向实验室用户的受控型 RNA-seq 对话 agent，用于降低分析发起门槛，同时保证流程可追溯、可审计、可复现。”**

文章的核心不应写成“做了一个聊天机器人”，而应写成：
- 它如何帮助实验室同学更容易发起分析
- 它如何把 GUI/chat/CLI 统一到同一个执行引擎
- 它如何保留 `project.json`、脚本、日志、状态和结果包这些审计产物

## 3. 生物信息流程 agent 一般如何落地

真正落地的生信 agent，通常不是替代 pipeline，而是包在 pipeline 外面，负责交互、组织、追踪和解释。

### 典型落地结构

1. **底层流程层**
   - 仍然是已有 pipeline / shell / HPC 任务

2. **执行编排层**
   - 负责上传、提交、轮询、下载、状态管理

3. **交互层**
   - GUI / chat / CLI 收集用户需求

4. **解释层**
   - 对状态、日志、结果做面向用户的解释

### 对我们项目的启发

我们现在这个仓库其实已经具备：
- 流程层
- 执行编排层

下一步最需要补的是：
- 更自然的对话入口
- 更强的参数采集与校验
- 结果报告和解释层

所以合理路线不是重写底层，而是：

**“保留现有 RNA-seq 执行底座，在上面补对话、报告和面向实验室用户的可用性。”**

## 4. 围绕 RNA-seq / WES / ChIP-seq 做问答 agent 体系

### 核心判断

不建议一开始同时深做三条流程。

### 推荐三阶段路线

1. **P1：先做 RNA-seq 完整闭环**
   - 问答引导
   - 配置生成
   - 后端执行
   - 状态回显
   - 结果解释
   - 报告生成

2. **P2：抽象通用 schema 和 adapter，再接 ChIP-seq**

3. **P3：最后再上 WES**
   - 因为 WES 在样本配对、变异注释、结果解释和隐私风险上最复杂

### 推荐分层

1. **知识问答层**：解释 RNA-seq / WES / ChIP-seq 是什么、需要准备什么
2. **任务路由层**：判断用户是在咨询还是要真正跑流程
3. **槽位采集层**：一步步补齐项目所需信息
4. **确定性执行层**：继续复用现有执行引擎
5. **结果解释层**：把状态、日志、结果翻译成实验室同学能理解的话

### 为什么这仍然算 agent

因为它仍然在做：
- 理解目标
- 多轮追问
- 调用工具
- 跟踪任务
- 解释结果

只是它是 **受控型 agent**，不是让 LLM 直接乱执行命令的自由型 agent。

## 5. 分析报告怎么设计

第一版不建议先做复杂前端，而建议先做 **标准化 Markdown 报告**。

原因是当前仓库已经有足够多的可追溯信息源，包括：
- `project.json`
- 运行状态
- 生成脚本
- 命令日志
- 事件日志
- 下载结果目录

### 第一版报告建议包含

1. **项目基本信息**
   - 项目 ID / 名称
   - 用户 / 时间
   - 分析类型
   - 服务器信息
   - 运行目录

2. **输入信息**
   - 本地 FASTQ 目录
   - 样本列表
   - 分组信息
   - 测序类型
   - 链特异性
   - 参考版本

3. **分析流程与参数**
   - 启用的步骤
   - 版本
   - 线程、内存、调度器
   - 轮询与通知设置

4. **运行状态摘要**
   - 当前状态
   - 提交时间 / 更新时间
   - job_id
   - 是否完成 / 失败 / 下载失败

5. **日志摘要**
   - 关键事件时间线
   - 命令摘要
   - 若失败，展示关键错误

6. **结果文件清单**
   - fastp 输出
   - STAR 日志
   - featureCounts 结果
   - RSEM 结果
   - Arriba 结果
   - 状态文件

7. **面向实验室同学的解释区**
   - 说明有哪些类型的结果
   - 哪些文件适合下游分析
   - 哪些内容仍需人工查看

8. **风险提示 / 未完成项**
   - 本报告只做整理，不替代生物学结论
   - 当前版本不自动给出科研结论
   - 关键结果仍需人工复核

### 为什么先做 Markdown

- 容易生成
- 容易版本管理
- 容易给老师和同学查看
- 后续容易转 HTML / PDF
- 不需要额外引入复杂前端

## 6. 怎么跑一个示例

当前仓库已经提供了示例配置文件：`examples/project.demo.json`。

### 最推荐的 demo 路线

围绕这个示例做一个最小闭环演示：

1. **加载或参考 demo 配置**
   - 项目 ID：`rnaseq_demo_001`
   - 已包含服务器、参考、样本、pipeline、polling、notification 示例

2. **先跑最小演示链路**
   - `gui` 或 `chat` 展示如何生成/查看配置
   - `validate-local` 演示本地 FASTQ 校验
   - `upload-command` 演示上传命令预览
   - `estimate` 演示耗时预估
   - `status` 演示状态查看入口

3. **若真实服务器和 FASTQ 已就绪，再跑完整链路**
   - `run project.json`
   - 自动上传、提交、轮询、下载
   - 形成 `runs/<project_id>/` 下的配置、脚本、日志、结果目录

4. **如果真实环境暂时不齐，也可以先做 dry-run 演示**
   - 重点展示“配置生成 + 校验 + 命令预览 + 目录结构 + 报告草案”
   - 先把产品逻辑讲清楚，再补真实运行结果

### 汇报时怎么讲 demo

可以说：

**“第一个示例不追求一开始就把所有真实环境全部接通，而是先围绕 `examples/project.demo.json` 做出一个可演示闭环，证明这个系统已经能完成配置、校验、执行组织和结果归档，随后再补真实运行案例。”**

---

## 总结

目前最合理的路线，不是同时大规模扩展所有功能，而是：

**先把当前项目收束成一个面向实验室同学的受控型 RNA-seq 对话 agent：上层负责问答、引导、配置和结果解释，下层继续复用现有确定性执行底座，再通过标准化报告和 demo 把它真正做成可落地的工具。**
