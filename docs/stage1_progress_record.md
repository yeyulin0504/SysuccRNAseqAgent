# SYSU RNA-seq Agent 阶段一试验记录

## 一、阶段说明

本阶段主要围绕项目接手、现状梳理、目标明确和总体路线设计展开，目的是把老师已经完成的大部分 RNA-seq agent 基础工程先看懂、讲清楚，并明确后续不再推倒重写，而是在现有执行底座上继续补对话能力、报告能力和可演示能力。

## 二、本阶段已完成内容

### 1. 项目整体结构与当前完成度梳理

已完成对整个项目的系统查看与理解，确认当前仓库已经不是单一脚本，而是一个可复用的 RNA-seq 流程执行底座，已经具备以下能力：

- 生成和保存 `project.json`
- 校验本地 FASTQ 输入
- 上传样本到远程服务器
- 生成远程分析脚本
- 通过 `slurm` / `pbs` / 本地方式提交任务
- 轮询任务状态
- 下载结果文件
- 发送通知

这说明项目底层执行能力已经比较完整，后续重点不应放在重写底层，而应放在用户交互和结果呈现层增强。

### 2. 项目定位和产品目标明确

已明确项目的真实目标不是做一个普通 GUI 软件，而是做一个面向实验室同学、低门槛、可以在各自电脑上使用的对话式 RNA-seq agent。

进一步明确了该 agent 的特点应为：

- GUI / chat / CLI 只是入口
- 核心仍然是统一执行引擎
- 项目过程要保留 `project.json`、脚本、日志、状态、结果包等可审计产物
- 后续可扩展到更多生信流程，而不是每个流程重写一套软件

### 3. 老师布置前六项任务的分析整理

已围绕老师提出的六项任务形成完整文字汇报，整理成文档：

- [docs/teacher_report_tasks_1_6.md](docs/teacher_report_tasks_1_6.md)

该部分已完成的内容包括：

1. 调研别人的 agent 常见发布方式
2. 梳理 agent 文章常见写法和应包含要素
3. 总结生物信息流程 agent 的典型落地结构
4. 设计 RNA-seq / WES / ChIP-seq 的阶段性建设路线
5. 设计分析报告应包含的内容结构
6. 明确当前项目的最小 demo 演示思路

### 4. 关于“这是不是 agent”的概念澄清

已完成对以下关键概念的解释和整理：

- 该项目与传统软件的区别
- 不让 LLM 直接执行系统命令，是否仍然算 agent
- 为什么受控型、可审计型、多轮交互型系统依然属于 agent

最终形成的共识是：

本项目属于“受控型生信 agent”，其核心不是自由执行命令，而是围绕用户目标进行多轮信息收集、调用工具、跟踪任务和解释结果。

### 5. 项目阶段路线初步确定

已形成清晰的分阶段建设思路：

- 第一优先级：先把 RNA-seq 做成完整闭环
- 第二优先级：补对话入口、报告输出、示例演示
- 第三优先级：后续再考虑 ChIP-seq 与 WES 扩展

其中 WES 被明确放在更后阶段，因为其在隐私、结果解释、样本设计和复杂度方面更高。

## 三、本阶段形成的关键判断

1. 当前项目基础执行引擎已经较完整，可以继续沿用。
2. 后续工作重点是“可用性增强”，不是“底层重构”。
3. 对实验室同学最合适的形态，是本地可用的对话式入口。
4. 报告和结果解释能力是后续 agent 化的重要组成部分。
5. 初期不宜同时深做 RNA-seq、WES、ChIP-seq 三条流程，应先做 RNA-seq 闭环。

## 四、本阶段产出材料

- 项目前六项任务汇报文档：`docs/teacher_report_tasks_1_6.md`
- 示例运行报告：`runs/report_demo.md`
- 已有示例配置：`examples/project.demo.json`

## 五、本阶段存在的问题

1. 目前仍以 RNA-seq 为核心，尚未扩展到更多流程。
2. 项目虽然具备执行能力，但对普通实验室同学来说入口仍不够自然。
3. 还缺少更贴近日常使用场景的对话体验。
4. 结果解释仍需进一步增强，当前还不能直接形成完整科研结论。
5. 真实 FASTQ 数据和真实服务器环境下的完整闭环演示尚未完成。

## 六、下一阶段计划

下一阶段重点从“理解项目、明确目标”转向“增强交互体验、形成可展示成果”，包括：

- 将项目进一步改造成对话式 agent
- 补充可复用的报告生成能力
- 优化状态查看与项目会话能力
- 增加结果解释入口
- 为后续实验室实际使用打基础
